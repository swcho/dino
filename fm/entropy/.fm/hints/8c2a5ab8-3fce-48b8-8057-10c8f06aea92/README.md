# `h_mean` — 코드북을 골고루 쓰는가

> **한 줄**: $h_{\text{mean}}$은 **평균 분포의 엔트로피**다. 프로토타입(코드)이 데이터 전체에서 얼마나 골고루 쓰이는지를 재며,
> 건강할 때 $\log K$가 아니라 **$\log(\text{실제 클러스터 수})$** 근처에 머문다. 토이에서는 $\log 6 \approx 1.79$.

---

## 1. 정의와 코드 — 순서가 전부다

$$h_{\text{mean}} = h(\bar q), \qquad \bar q = \frac{1}{N}\sum_{x} q(x)$$

```python
h_mean = entropy(q.mean(0)).item()     # 평균을 먼저, 엔트로피를 나중에
h_each = entropy(q).mean().item()      # 엔트로피를 먼저, 평균을 나중에
```

`q`는 `(N, out_dim)` 짜리 teacher 출력 확률이다. 두 지표의 코드는 `.mean(0)`과 `entropy(...)`의 **순서만** 다르다.
그런데 그 순서가 재는 대상을 완전히 뒤집는다.

| | 연산 | 재는 것 | 계기판 |
|---|---|---|---|
| `h_each` | $\frac{1}{N}\sum h(q(x))$ | 점 **하나하나**가 확신하는가 | sharpening |
| `h_mean` | $h\!\left(\frac{1}{N}\sum q(x)\right)$ | 코드가 **골고루** 쓰이는가 | centering |

`.mean(0)`을 먼저 하면 개별 점의 뾰족함은 평균 속에서 지워진다 — 남는 것은 "각 차원이 전체적으로 얼마나 자주 뽑혔나"뿐이다.

> 형제 카드에서 다룬 대로 Jensen 부등식에 의해 항상 $h_{\text{mean}} \ge h_{\text{each}}$이고,
> 그 차이 $h_{\text{mean}} - h_{\text{each}} = I(X; Z)$가 상호정보량이다. 이 카드는 그 **위쪽 항 하나**를 계기판으로 읽는 법이다.

---

## 2. 무엇을 재는가 — 코드북 사용률(codebook utilization)

$\bar q$의 $k$번째 성분은

$$\bar q_k = \frac{1}{N}\sum_x q_k(x) = \Pr[\text{프로토타입 } k \text{ 가 선택될 확률}]$$

즉 $\bar q$는 **코드북 사용 히스토그램**이다. 그 엔트로피가 높다 = 프로토타입들이 고르게 나눠 쓰인다.
낮다 = 소수의 프로토타입이 데이터를 독식하고 나머지는 죽어 있다.

이건 DINO만의 이야기가 아니다. 같은 현상이 여러 이름으로 불린다.

| 분야 | 이름 | 증상 |
|---|---|---|
| VQ-VAE / VQ-GAN | **codebook collapse** | 8192개 코드 중 실제로 200개만 쓰임 |
| k-means | **empty cluster** | 어떤 중심에도 점이 안 붙어 갱신이 멈춤 |
| DINO | **원-핫 붕괴** | `top_share` → 1.0, 한 차원이 전부 |
| MoE 라우팅 | **expert collapse** | 라우터가 소수 전문가에만 몰림 (load-balancing loss로 대응) |

VQ-VAE 쪽에서 쓰는 코드북 사용률 지표가 정확히 $e^{h(\bar q)}$이고,
MoE의 load-balancing loss는 $\bar q$를 균등에 가깝게 미는 항이다.
**DINO의 centering은 이 계열의 정규화와 같은 역할을 아키텍처가 아니라 로짓 보정으로 해내는 장치다.**

## 3. ★ 왜 건강한 값이 $\log K$가 **아니라** $\log(\text{클러스터 수})$인가

이 카드에서 제일 헷갈리는 지점이고, 이 지표를 잘못 읽게 만드는 주범이다.

토이의 `out_dim=32`이므로 $\log K = \log 32 = 3.47$이 이론적 최대다. 그런데 **데이터에는 실제로 6개 클러스터밖에 없다.**
이상적인 모델이라면 6개 클러스터에 6개 코드를 1:1로 붙이고 **나머지 26개는 비워 둔다.** 그러면

$$\bar q \approx \left(\tfrac16, \tfrac16, \tfrac16, \tfrac16, \tfrac16, \tfrac16, 0, \dots, 0\right)
\quad\Longrightarrow\quad h_{\text{mean}} \to \log 6 = 1.79$$

$\log 32 = 3.47$이 아니다. 그리고 **$h_{\text{mean}}$이 $\log K$까지 올라가면 그건 오히려 나쁜 신호다** —
32개 코드를 전부 균등하게 쓴다는 건, 데이터에 6개 구조밖에 없는데 억지로 32갈래로 흩뿌렸다는 뜻이다.
그게 바로 **균등 붕괴**다.

```
h_mean 의 스펙트럼 (toy, K=32, 실제 구조 6개)

  0 ─────────── 1.79 ────────────── 3.47
  ↑              ↑                    ↑
원-핫 붕괴      건강 = log 6         균등 붕괴 = log K
(코드 1개)     (코드 6개)           (코드 32개 균등)
     ← 나쁨         좋음                나쁨 →
```

> **"높을수록 좋다"가 아니다.** $h_{\text{mean}}$은 **양쪽 끝이 다 병**이고 중간이 건강한 지표다.
> `h_each`(낮을수록 확신 = 좋음)와 달리 단조 지표가 아니라서 대시보드에서 무심코 보면 반드시 오독한다.
> $\log K$라는 상한선을 목표선으로 착각하는 순간 균등 붕괴를 "성공"으로 읽게 된다.

이 비직관성의 근원: $h_{\text{mean}}$의 상한 $\log K$는 **모델의 용량**이 정하지만,
건강한 값 $\log(\text{클러스터 수})$는 **데이터가 가진 구조**가 정한다. 둘은 애초에 다른 것이 결정하는 숫자다.
$K$는 우리가 넉넉하게 잡은 예산이고, 예산을 다 쓰는 게 목표가 아니다.

## 4. perplexity로 읽어라 — $e^{h_{\text{mean}}}$ = 실효 코드 수

엔트로피의 nat 값은 감이 안 온다. 지수를 취하면 바로 개수가 된다.

$$\text{perplexity} = e^{h_{\text{mean}}} = \text{"실효적으로 사용 중인 코드 수"}$$

$\bar q$가 정확히 $n$개 코드에 균등하면 $e^{h(\bar q)} = n$. 불균등하면 그보다 작게 나온다.
**$h_{\text{mean}}$을 볼 때는 항상 머릿속에서 $e^{(\cdot)}$을 취하는 습관을 들여라.**

토이 `both = DINO` 설정의 실측 $h_{\text{mean}} = 2.38$ → $e^{2.38} \approx 10.8$.
"코드가 6개 붙었다"고 했는데 왜 11인가?

- argmax 기준으로는 **정확히 6개 코드**만 쓰인다 (`code_acc = 1.00`, `top_share = 0.17 = 1/6`).
- 하지만 $q$는 원-핫이 **아니라** soft 분포다. `h_each = 0.59`만큼의 잔여 확률이 주변 코드로 새어 나간다.
- 그 누수가 $\bar q$의 꼬리를 채워 실효 코드 수를 6 → 11로 부풀린다.

즉 **$h_{\text{mean}}$은 hard 코드 수의 상한**이다. 정확히 몇 개가 쓰이는지 알고 싶으면
`q.argmax(-1).unique().numel()`을 같이 찍어야 한다 — 노트북의 산점도 제목이 `n codes used`를 함께 표시하는 이유다.

### 실제 DINO에서의 감각

원본 DINO는 `--out_dim 65536`, 즉 $\log K = 11.09$다. 그런데 기대할 값은 그 근처가 아니다.

| 기준 | $h_{\text{mean}}$ | perplexity |
|---|---|---|
| ImageNet 클래스 수만큼 쓴다면 | $\log 1000 = 6.91$ | 1000 |
| 실제 건강한 DINO | 이보다 **다소 높음** | 수천 |
| $\log K$ (균등 붕괴) | $11.09$ | 65536 |
| 원-핫 붕괴 | $\to 0$ | $\to 1$ |

DINO가 잡는 구조는 "1000개 클래스"보다 세밀하다 — 견종, 자세, 배경, 텍스처 같은 하위 구조까지 코드가 갈린다.
그래서 실효 코드 수는 1000보다 크지만, 65536 전부를 쓰는 것과는 거리가 멀다.
**`out_dim=65536`은 목표가 아니라 넉넉한 예산이다.** 넉넉히 잡아두고 실제로 쓰이는 만큼만 쓰게 두는 설계.

## 5. ★ 실전 함정 — 배치 안에서 계산하면 $\log B$에 갇힌다

이 지표를 실제로 로깅할 때 거의 반드시 밟는 함정이다.

배치 하나($B$개 샘플)로 $h(\bar q)$를 계산하면, 상호정보량 분해에서

$$h_{\text{mean}} - h_{\text{each}} = I(X;Z) \le H(X) \le \log B$$

$X$가 배치 안의 $B$개 샘플만 훑기 때문이다. 특히 sharpening이 잘 걸려 $h_{\text{each}} \approx 0$인 건강한 상태에서는

$$h_{\text{mean}} \lesssim \log B$$

**즉 배치가 작으면 진짜 값이 얼마든 그 위로는 절대 못 올라간다.** 실측으로 확인하면:

| 배치 | 측정된 $h_{\text{mean}}$ | 천장 $\log B$ | 참값 $\log 1000$ |
|---|---|---|---|
| $B = 256$ | **5.38** | 5.55 | 6.91 |
| $B = 1024$ | **6.36** | 6.93 | 6.91 |
| $B = 4096$ | **6.77** | 8.32 | 6.91 |
| 에폭 누적 (1.28M) | **6.91** ✅ | — | 6.91 |

> (실제로 1000개 코드를 하드 할당하는 이상적 모델을 시뮬레이션한 값. $B=256$에서는 참값 6.91이 천장 5.55보다 위라 **원리적으로 관측 불가**다.)

DINO 기본 설정(GPU당 64 × 16 GPU ≈ 1024)에서 $\log 1024 = 6.93$이다.
그런데 비교 대상인 $\log 65536 = 11.09$다. **애초에 도달할 수 없는 숫자와 비교하고 있는 것이다.**
"$h_{\text{mean}}$이 6.4밖에 안 나오네, 코드북을 절반도 못 쓰나?"라는 진단은 100% 틀린 진단이다 — 배치가 작았을 뿐이다.

**대책**:
1. 코드 히스토그램 `counts`를 **에폭 단위로 누적**한 뒤 정규화해서 엔트로피를 계산한다. (표의 마지막 줄)
2. 배치 단위 값을 쓸 거라면 **절대값이 아니라 추세**만 본다 — 같은 배치 크기끼리의 시계열 비교는 유효하다.
3. 절대값을 보고 싶다면 반드시 $\log B$ 선을 대시보드에 같이 그린다. 노트북이 $\log 32$와 $\log 6$ 보조선을 둘 다 그리는 것과 같은 이유다.
4. 분산 학습에서는 `all_reduce`로 전 프로세스 히스토그램을 모아야 $B$가 실제 글로벌 배치가 된다 — `update_center`가 `dist.all_reduce`를 쓰는 것과 같은 사정.

## 6. centering이 직접 미는 값

`MiniDINOLoss.update_center`를 보면:

```python
batch_center = teacher_output.mean(dim=0, keepdim=True)
self.center = self.center * self.center_momentum + batch_center * (1 - self.center_momentum)
```

그리고 forward에서 `(teacher_output - center) / temp`.

**자주 큰 값을 내는 차원 → `center`가 커짐 → 다음 스텝에 그만큼 더 깎임 → 억제.**
이 음의 피드백이 정확히 $\bar q$를 균등 쪽으로 미는 힘이다.

즉 **$h_{\text{mean}}$은 centering의 계기판이다.**
`h_each`가 sharpening의 계기판인 것과 정확히 대칭이고, 두 장치가 서로 반대 방향으로 미는 구조가 두 지표에 그대로 나타난다.

```
centering  ──(밀어 올림)──▶  h_mean   ──(Jensen: h_mean ≥ h_each)
                                ▲
                                │  차이 = I(X;Z) = 표현이 담은 정보
                                ▼
sharpening ──(눌러 내림)──▶  h_each
```

`h_mean`이 계속 떨어진다 = **centering이 약하다** → `center_momentum`, 배치 크기, `all_reduce` 경로를 의심.
`h_mean`이 $\log K$에 붙는다 = **centering만 이기고 sharpening이 죽었다** → `teacher_temp` 확인.

## 7. 토이 4개 설정 실측치 (1500 steps, `out_dim=32`)

`log 32 = 3.47`, `log 6 = 1.79`

| 설정 | `h_each` | `h_mean` | $e^{h_{\text{mean}}}$ | 실제 코드 수 | `top_share` | `code_acc` |
|---|---|---|---|---|---|---|
| **none** (center✗ temp 0.1) | 2.90 | **3.01** | 20.2 | **2** | 0.83 | 0.33 |
| **center only** (center✓ temp 0.1) | 3.36 | **3.46** | 31.9 | 6 | 0.33 | 0.83 |
| **sharp only** (center✗ temp 0.04) | 0.00 | **1.24** | 3.5 | 4 | 0.50 | 0.67 |
| **both = DINO** (center✓ temp 0.04) | 0.59 | **2.38** | 10.8 | **6** | 0.17 | **1.00** |

### 한 줄씩 읽기

**none — `h_mean = 3.01` (perplexity 20)이지만 실제 코드는 단 2개.**
이 줄이 3절 경고의 살아있는 증거다. $h_{\text{mean}}$만 보면 "20개 코드를 쓰는 중"으로 읽히지만,
argmax를 세어보면 2개뿐이고 `top_share = 0.83`으로 한 코드가 데이터의 83%를 먹었다.
$q$가 전체적으로 밋밋하게 퍼져 있어(`h_each = 2.90`) $\bar q$도 밋밋할 뿐, 그 밋밋함 위에 **미세한 공통 편향**이 얹혀 argmax를 독점한 것이다.
$h_{\text{mean}}$ 하나만 보고 판단하면 안 되는 이유 — **반드시 `h_each`, `top_share`와 짝으로 본다.**

**center only — `h_mean = 3.46`, $\log 32 = 3.47$과 사실상 같다. perplexity 31.9 ≈ 32.**
교과서적인 **균등 붕괴**다. 32개 코드를 전부, 완벽하게 균등하게 쓰고 있다.
"코드북 사용률 100%"인데 표현은 쓸모없다 — `h_each = 3.36`도 같이 천장이라 개별 점이 아무것도 확신하지 않기 때문.
centering이 혼자 이겼을 때 어디로 가는지를 보여주는 상한 사례. **$h_{\text{mean}}$ 최대화가 목표가 아님을 이 한 줄이 증명한다.**

**sharp only — `h_mean = 1.24`, perplexity 3.5.**
$\log 6 = 1.79$보다 **낮다**. 6개 클러스터가 실효 3.5개 코드로 뭉개졌다는 뜻이고,
실제로 코드 4개에 `top_share = 0.50` — 한 코드가 데이터 절반을 삼켰다.
`h_each = 0.00`(완벽한 확신)과 짝지으면 **원-핫 붕괴로 가는 중**이라는 진단이 나온다.
전형적인 codebook collapse의 초기 모습이고, 이때 loss는 0.22로 네 설정 중 **가장 낮다** — loss는 이 붕괴를 전혀 못 잡는다.

**both = DINO — `h_mean = 2.38`, perplexity 10.8, 실제 코드 6개, `code_acc = 1.00`.**
$\log 6 = 1.79$와 $\log 32 = 3.47$ 사이 중간 지대에 안정적으로 자리 잡았다.
perplexity 10.8이 6보다 큰 건 4절에서 본 대로 soft 분포의 꼬리 누수 때문이지, 코드를 낭비해서가 아니다.
`h_each = 0.59`(낮음, 확신) + `h_mean = 2.38`(중간, 골고루)의 조합 —
**두 값의 차이 $2.38 - 0.59 = 1.79$가 바로 $I(X;Z)$이고, 우연찮게도 정확히 $\log 6$이다.**
6개 클러스터를 완벽히 구분하는 데 필요한 정보량이 그대로 표현에 담겼다는 뜻. 레이블은 한 번도 보지 않았는데.

## 요약 — 이 카드가 남길 것

1. $h_{\text{mean}} = h(\bar q)$, `entropy(q.mean(0))`. **평균 먼저, 엔트로피 나중** (`h_each`와 반대 순서).
2. 재는 것은 **코드북 사용률**. VQ-VAE의 codebook collapse, k-means의 empty cluster와 같은 병.
3. 건강한 값은 $\log K$가 **아니라** $\log(\text{클러스터 수})$. 토이에서 $\log 6 = 1.79$. **$\log K$ 도달은 균등 붕괴 신호.** 높을수록 좋은 지표가 아니다.
4. 항상 $e^{h_{\text{mean}}}$(실효 코드 수)으로 환산해 읽는다. `both`는 2.38 → 11개.
5. 배치 안에서 재면 대략 $\log B$에 갇힌다. $B=1024$면 6.93이 천장이라 $\log 65536 = 11.09$와의 비교는 무의미. **에폭 단위 히스토그램 누적**이 답.
6. $h_{\text{mean}}$은 **centering의 계기판** (`h_each`는 sharpening의 계기판).
7. 단독으로 읽지 말 것. `h_each` · `top_share` · 실제 코드 수와 **짝으로** — `none` 설정이 $h_{\text{mean}}=3.01$인데 코드를 2개만 쓰는 반례다.
